# 3 PLAN — 시나리오 카탈로그

목표: `qa/inventory.json` 을 **실행 가능한 시나리오**로 바꿔 `qa/SCENARIOS.md` 에 남긴다.
이건 이번 실행용 스크립트가 아니라 **프로젝트에 누적되는 자산**이다.

템플릿: `assets/SCENARIOS-template.md`

---

## 기존 문서가 있으면 병합한다

먼저 찾는다:

```bash
find . -iname '*e2e*.md' -o -iname '*scenario*.md' -o -iname '*qa*.md' | grep -v node_modules
ls qa/SCENARIOS.md 2>/dev/null
```

있으면:

- **기존 ID 를 보존한다.** `S6` 이 이미 "응시 전체 흐름"이면 계속 그 뜻이어야 한다. ID 가 바뀌면
  과거 리포트·이슈 로그와의 연결이 끊긴다
- 새로 찾은 페이지만 새 ID 로 **추가**한다
- 기존 항목이 코드와 안 맞으면(라벨 변경, 라우트 삭제) 지우지 말고 **`⚠ 코드와 불일치` 로 표시**한다.
  문서가 틀린 건지 코드가 회귀한 건지는 실행해 봐야 안다
- 덮어쓰기 전에 확인받는다

## ID 규칙

`<스위트문자><번호>` — 예: `L1`, `A5`, `S6`, `D12`. 변형은 하이픈: `A5-b`, `D12-c`.

스위트 문자는 프로젝트마다 다르게 잡는다. **역할 또는 사용자 여정 기준**으로 나눈다:

| 예시 문자 | 스위트 | 기준 |
|---|---|---|
| `L` | 공개/랜딩 | 인증 없이 도달 |
| `A` | 신청·가입 | 주 진입 플로우 |
| `S` | 사용자 핵심 기능 | 로그인 후 주 사용 여정 |
| `R` | 결과·조회 | 읽기 중심 |
| `X` | 예외·보안 | 위반·권한·세션 |
| `D` | 관리자 | 역할 격리 |
| `G` | 회귀 | 과거 버그 재발 방지 |

**한 번 부여한 ID 는 재사용하지 않는다.** 항목이 없어져도 번호를 비워둔다.

## 시나리오 하나의 형식

```markdown
### S6. 응시 — 전체 흐름 ★
- **전제**: 대상 시험이 현재 응시 가능 창 안 (D12-b 로 세팅)
- **역할**: 학생
- **단계**:
  1. 시험 상세 → `시험 시작` → 모달 확인
  2. 응시자 정보 확인 → `시험 진행`
  3. 문항 답 선택 → `답안 제출`
- **기대**: 각 단계 전이 정상, 제출 200, 점수 페이지 도달
- **증거**: `POST /api/student/submit` 200, 화면 문구 `채점 결과 보러 가기`
- **금지 문구**: `응시가 종료되었습니다.` ← 뜨면 실패 (선택)
- **주의**: 다른 탭으로 포커스 이동 금지(이탈 감지에 걸림)
```

- **전제**를 반드시 적는다. 대부분의 E2E 실패는 실제 실패가 아니라 전제 미충족이다
- **기대**는 관찰 가능해야 한다. "정상 동작"이 아니라 **화면 문구·상태코드·배지 텍스트**로 쓴다
- **금지 문구**는 선택이지만 있으면 **판정이 기계적이 된다.** 회귀 스위트에서만 쓰던 장치인데
  일반 시나리오에도 똑같이 쓸 수 있다 — 실패를 문자열 하나로 확정할 수 있으면 적는다
- ★ 는 스모크 필수 표시 (선정 기준은 아래 §실행 순서)
- 다른 시나리오에 의존하면 그 ID 를 적는다(`D12-b 로 세팅`)

## 커버리지 — 인벤토리 종류마다

`inventory.json` 의 **네 배열 각각**에 최소 커버리지가 있다. 페이지만 시나리오로 바꾸면
API 전용 서버(NestJS·Express·FastAPI)에서 검증 대상이 통째로 빈다.

### `pages` — 4축

페이지마다 **최소 이 4개**. 해피패스만 쓰지 않는다:

1. **해피패스** — 의도된 대로 성공
2. **경계** — 마감 직전/직후, 0건, 최대치
3. **권한** — 다른 역할로 접근, 미인증 직접 URL
4. **에러** — 잘못된 입력, 서버 실패 시 사용자에게 보이는 것

### `apis` — 4종

계약(`contracts/api-spec.md`·OpenAPI)이 있으면 **계약이 기대값**이고 불일치는 그 자체로 이슈다.

| 종류 | 기대 |
|---|---|
| 미인증 | 401 (또는 로그인 리다이렉트) |
| 타 역할 | 403 — **200 이 나오면 그건 보안 이슈다** |
| 잘못된 입력 | 4xx + 에러 본문 형식이 규약대로인가 |
| 정상 | 2xx + **GET 으로 되읽어 실제 반영 확인** |

웹 UI 가 있는 프로젝트에서도 권한·에러 케이스는 API 로 확인하는 게 화면보다 싸고 정확하다.
UI 가 없는 프로젝트면 **이게 E2E 를 대신하는 본체**다 — `skip` 이 아니라 정식 검증이다.

### `roles` — 교차 위반

역할 × 접근 가능 라우트 매트릭스에서 **대각선 밖**을 시나리오로 만든다. 역할 N개면
"남의 영역에 직접 URL 진입" 케이스가 최소 N×(N−1) 개 나온다. 전부 돌 필요는 없고
**민감한 것부터** — 관리자 영역, 남의 개인정보, 결제 이력.

세션 저장소가 영역마다 다르면 별도 브라우저 프로필이 필요하다 (`discovery.md` §3).

### `sideEffects` — 3단

1. **테스트 모드가 있는가** — 테스트 결제키·메일 캐처·dev 무발송. 있으면 그 모드로 검증
2. 없으면 **실행 전 확인** 대상으로 시나리오에 표시 (안전 규칙 3)
3. **되돌리기 경로가 있는가** — 없으면 시나리오에 그 사실을 적는다. 되돌릴 수 없는 것을
   확인 없이 돌리지 않는다

### 선택 축 — 반응형

모바일 폭(360px 등)에서 레이아웃이 깨지는지. **필수는 아니지만** 디자인 기준이 있는 프로젝트
(하네스면 `contracts/design-guide.md`)에서는 넣을 가치가 크다. 넣기로 했으면 주요 페이지에만
붙이고 시나리오 ID 에 `-m` 변형을 쓴다 (`S6-m`).

## 회귀 스위트(G)

**과거에 실제로 터졌던 버그**만 넣는다. 소스:

```bash
git log --oneline --grep='fix\|버그\|hotfix' -i -30
ls docs/changes/ 2>/dev/null
grep -rn "⚠️\|FIXME\|알려진\|known issue" docs/ 2>/dev/null | head -20
```

각 항목에 **금지 문구**를 적으면 판정이 기계적이 된다 — "상세에 `응시가 종료되었습니다.` 가 뜨면 회귀".

**알려진 미해결 이슈**는 회귀 스위트에 `⚠ 알려진 백로그` 로 표시한다. 실행자가 신규 버그로 오인해
같은 이슈를 반복 보고하는 걸 막는다.

## 실행 순서를 같이 낸다

SCENARIOS.md 말미에 두 가지 순서를 적는다:

- **스모크 (30~40분)** — ★ 항목만, 핵심 여정 한 바퀴
- **전체** — 스위트 순서 + 각 스위트의 전제 세팅 단계

**의존 순서를 지킨다.** 관리자에서 데이터를 만들어야 사용자 시나리오가 돌아가면 관리자 스위트가 앞이다.

### ★ (스모크 필수) 선정 기준

전체에서 한 바퀴를 뽑는 기준. 위에서부터 우선한다:

1. **돈이 움직이는 경로** — 결제·환불·정산
2. **역할별 주 진입 1개씩** — 각 역할이 로그인 후 처음 하는 일
3. **부수효과가 있는 것** — 메일·SMS·파일생성·외부 호출
4. **과거 회귀 이력** — G 스위트에 있는 항목
5. **인증·권한 게이트** — 뚫리면 즉시 보안 이슈

기준일 뿐 강제가 아니다. 프로젝트 성격에 따라 사용자와 조정한다 — 조정했으면 그 근거를
SCENARIOS.md 에 한 줄 남긴다.

---

## 실행 전에 사용자에게 보여준다

SCENARIOS.md 를 쓴 다음, **바로 실행하지 말고** 요약을 제시한다:

- 스위트별 항목 수와 예상 소요
- 사용자 입력이 필요한 지점(로그인·OTP·결제)
- 사전 확인이 필요한 파괴적 액션
- `blocked` 가 예상되는 항목과 이유

여기서 범위를 조정받고 시작한다. 다 돌고 나서 "사실 이건 못 했다"보다 훨씬 싸다.
