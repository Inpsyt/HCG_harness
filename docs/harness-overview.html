Portable Multi-Agent Development Harness

규율 위에서 동작하는
멀티에이전트 개발 하네스

5개 역할 에이전트가 contracts(단일 진실원) 위에서 plan→구현→qa 파이프라인을 돌고, hook이 규약을 실행 시점에 강제하며, 대량·독립 작업은 워크플로로 팬아웃합니다. 이 전체를 Claude Code 플러그인으로 패키징해, 어느 프로젝트든 설정 한 장으로 장착합니다.

00
00 · Overview

한 줄로 — 무엇인가

개별 AI의 코딩 능력을 그대로 두되, 그 위에 역할 분담 · 공유 계약 · 검증 게이트 · 실행 강제라는 골격을 씌운 개발 방법론입니다. 그리고 그 골격을 프로젝트마다 다시 짜지 않도록 이식 가능한 플러그인으로 만들었습니다.

정의

contracts를 블랙보드 SSOT로 두고, 5 역할 에이전트가 정적 파이프라인(결합 기능) 또는 fast-path(소규모)로 일하며, 4 hook이 규약을 강제하고, 무거운 작업은 5 워크플로로 팬아웃하는 — 포터블 멀티에이전트 개발 하네스.

01
01 · Rationale

왜 범용 플러그인으로 만들었나

잘 만든 멀티에이전트 셋업도 프로젝트마다 복붙하면 세 가지가 무너집니다 — 사본이 서로 갈라지고(드리프트), 품질이 사람·프로젝트마다 들쭉날쭉해지고, 한 곳의 개선이 다른 곳에 전파되지 않습니다.

그래서 방법론·역할·안전장치·스택 컨벤션을 한 번 패키징해 Claude Code 플러그인으로 배포합니다. 설치하면 프로젝트의 .claude/ 위에 additive로 합류합니다(기존 설정을 덮지 않음). 핵심은 2층 분리입니다 — 방법론은 재사용, 프로젝트 고유값만 인스턴스화.

Portable — 플러그인이 들고 다님

재사용 (손대지 않음)

  • 파이프라인 · fast-path · Operating Rules
  • 5 에이전트 역할 셸 (제네릭)
  • 7 스킬 · 4 hook · 5 워크플로
  • HCG 표준 스택 컨벤션
Per-project — 소비 프로젝트가 채움

인스턴스화 (한 장 + α)

  • .claude/project.md — 유일 슬롯
  • 도메인 스킬 (비즈니스 규칙)
  • contracts/* (계약 인스턴스)
  • 앱 코드 · DB
Benefit

즉시 도입

새 프로젝트가 project.md 한 장 + 도메인 스킬만 채우면 전체 파이프라인이 붙습니다. 하네스 재작성 0.

Benefit

단일 출처 진화

방법론을 한 번 개선하면 플러그인을 소비하는 모든 프로젝트가 함께 좋아집니다 — 사본 드리프트 제거.

Benefit

품질 일관

모든 프로젝트가 동일한 검증 게이트·안전장치·스택 컨벤션을 공유합니다.

Benefit

도메인 비종속

포터블 층엔 프로젝트 도메인 문자열 0. 표준 스택 위라면 어디든 동일하게 작동.

참고 · 비유로는 "꽂아 쓰는 표준 부품(USB)" — 방법론 전체를 한 번에 장착하고, 이 프로젝트의 이름·경로만 끼웁니다.

02 · Architecture

아키텍처 / 구조

레포 자체가 단일 플러그인 마켓플레이스입니다. 플러그인 본체가 5개 구성요소(에이전트·스킬·hook·워크플로·방법론 코어)를 담고, 소비 프로젝트는 슬롯과 계약을 인스턴스화합니다.

# 레포 = 단일 플러그인 마켓플레이스 hcg_harness/ ├─ .claude-plugin/marketplace.json # 마켓플레이스 정의 ├─ hcg-harness/ # ◀ 플러그인 본체 │ ├─ .claude-plugin/plugin.json # 매니페스트 │ ├─ CLAUDE-core.md # 파이프라인 · fast-path · Rules §0~§5 │ ├─ agents/ (5) plan · qa · db · backend · front │ ├─ skills/ (7) 프로세스 3 · 계약 1 · 스택 3 │ ├─ hooks/ (4) guard · verify · context · gate │ └─ workflows/(5) audit · review · converge · migrate · test-gen ├─ templates/ # project.md · CLAUDE.md · codex-review.mjs · ci-drift └─ docs/ # install · 경계 · 벤치마크

구성요소 관계 — contracts를 중심으로

contracts/(SSOT)가 한가운데 있고, 모든 흐름이 그것을 기준으로 돕니다 — plan이 계약을 쓰고, db/backend/front가 읽어 구현하고, qa가 계약과 대조해 검증합니다. skills는 각 에이전트에 방법론을 주입하고(spawn 시 preload), hooks는 그 규약을 실행 시점에 강제하며, 독립·대량·읽기 작업은 workflows로 팬아웃합니다.

Core

contracts/ · 블랙보드 SSOT

db-schema · api-spec · shared-types · design-guide. plan만 쓰기(기본 잠금), 나머지는 읽기. 모든 Task가 여기서 파생됩니다.

Slot

.claude/project.md · 유일 슬롯

정체성·경로·스택·모델 배정·활성 에이전트. 에이전트 셸이 spawn 시 Read 해 인스턴스값을 주입받습니다.

④ verification ladder — 가장 강한 rung으로 검증

rung방법적용

3실행 스모크 / 재현 절차경로 직접 실행
4명시 수용기준 + diff (사람=검증자)UI·탐색·재현난해
역할 — TDD를 대체하는 요소

“다 됐다”는 말 대신 증거를 요구하되, 증거에도 등급을 매겨 가능한 가장 강한 검증을 쓰게 하는 규율입니다. 이는 TDD(테스트 우선 개발)의 “항상 테스트부터”라는 단일 규칙을 일반화한 것 — 테스트가 최선(rung 1)이지만 UI·탐색처럼 테스트가 어려운 일도 있으니, “검증 우선”이라는 TDD의 정신은 지키되 경직성은 버린, TDD를 대체하는 더 유연한 형태입니다.

HCG 표준 러너 · 단위·통합 = Vitest, E2E = Playwright. 적대적 게이트는 codex-review(⑤). 러너는 *-conventions 스킬이 규정.

⑤ codex 적대적 게이트 — KIND가 severity보다 먼저 (D9)

Phase 완료 시, 외부 모델(codex)이 누적 diff를 적대적으로 리뷰합니다. 단 핵심은 KIND 선분류입니다 — 적대적 리뷰어는 결함이 없어도 "추가하면 좋다"는 갭을 만들어내므로, 그걸 게이트에 그대로 태우면 과설계를 강제하게 됩니다.

KIND판정
게이트 대상정확성·안전 결함(crash·data loss·race·injection·auth bypass) 또는 명시 요구사항·계약 위반 → FAIL
부록 (비차단)gap/enhancement·over-design·스타일 — codex가 Critical/High로 매겨도 부록(게이트 PASS 유지)

⑥ hook 강제 — 규칙을 ‘문서’가 아니라 ‘자동 차단’으로

보통 “이건 하지 마”라는 규칙은 문서에 글로만 적혀 있어, 지켜질 거라 믿는 수밖에 없습니다. hook은 다릅니다 — 규칙을 어기는 도구 호출(파일 편집·명령 실행)이 실제로 실행되기 직전에 프로그램이 자동으로 가로막습니다. 방식은 단순합니다. hook이 끝나며 내보내는 exit 코드로 “통과시켜 / 막아”를 지시합니다 — 이게 강제의 전부입니다.

exit의미효과
0통과진행 (또는 stdout을 컨텍스트 주입)
2차단도구 호출 취소 + stderr 사유를 Claude에 피드백
—fail-open인프라 오류는 전부 0 — hook 버그가 작업을 막지 않음

설계 · PreToolUse 페이로드에 에이전트 식별자가 없어, "누가 호출했나"가 아니라 "지금 잠겨 있나"(의도)로 판정하는 intent-lock 채택. 실제 보안 경계는 OS /sandbox 권장(hook은 guardrail).

⑦ 두 가지 실행 모드 — 정적 vs 동적

결합 기능은 위 정적 파이프라인으로, 독립·대량·읽기 작업은 동적 워크플로(팬아웃)로 처리합니다. 모든 워크플로는 fail-closed — 열화/모호 시 "정상"이 아니라 incomplete를 반환합니다.

06 · At a glance

한눈에 — 설계 원칙

이 하네스를 관통하는 원칙들입니다. 도구가 아니라 규율이 핵심이며, 그 규율을 자기 자신에게도 적용합니다.

01
하나의 진실원 (SSOT)정답을 적어두는 곳은 contracts 한 곳뿐. 모든 작업이 거기서 나오고 검사도 그것만 기준으로 한다 — 서로 말이 달라질 수 없다.
02
막히면 멈춘다 (fail-closed)애매하거나 확인이 덜 된 결과는 “통과”가 아니라 “미완”으로 처리한다. 대충 OK를 내지 않는다.
03
필요한 만큼만 (과설계 억제)“있으면 좋은 것”은 만들지 않는다. 진짜 결함과 약속 위반만 막고, 나머지 제안은 참고로만 남긴다.
04
말이 아니라 작동 (실행 강제)규칙을 문서로만 두지 않는다. 프로그램(hook)이 위반을 실제로 가로막고, 안전장치가 고장 나도 일은 멈추지 않게 한다.
05
되돌릴 수 있게 (안전 우선)되돌리기 어렵거나 위험한 일(삭제·결제·보안)은 더 신중한 전체 절차로 다루고, 파괴적 명령은 아예 차단한다.
06
솔직하게 (정직한 보고)증거 없는 자기 자랑은 스스로 깎는다. 안 된 건 안 됐다고 말한다 — 자기 자신을 평가할 때도 똑같이.
결론

AI의 속도는 그대로 두고, 그 위에 역할·계약·검증·강제의 골격을 씌운다. 그리고 그 골격을 플러그인으로 만들어 모든 프로젝트가 같은 규율을 즉시 장착한다 — 그것이 이 하네스 엔지니어링입니다.

도입 대상 · 팀·코드를 빠르게 키우는 조직, 품질·안전이 신뢰인 제품, AI 코딩을 개인 재능이 아니라 조직 표준으로 만들려는 팀.
