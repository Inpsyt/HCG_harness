1부 · 왜 바꿨나 — S1

일하는 방식이 코드와 함께 산다

하네스 = AI 에게 개발을 시킬 때 따르게 하는 회사 표준 작업 규칙 묶음입니다. 비유하면 업무 표준 매뉴얼 — 신입이 와도 서랍에 매뉴얼이 있으면 같은 품질이 나오듯, 우리는 그 매뉴얼을 프로젝트 폴더 안에 넣어둡니다.

AI 와의 대화 한 판을 세션이라고 부르는데, 세션은 끝나면 기억이 사라집니다. 그래서 규칙을 사람 머릿속이 아니라 파일로 둡니다 — 누가, 언제, 몇 번째 세션을 열어도 AI 가 매뉴얼을 먼저 읽고 같은 방식으로 일합니다.

프로젝트 폴더/
├─ CLAUDE.md            ← 매뉴얼 입구 (AI 가 세션마다 자동으로 읽음)
├─ .claude/project.md   ← 이 프로젝트의 값 (기술 구성·경로·사용 규모)
├─ contracts/           ← 계약서 4종 = 단일 정답 문서(SSOT)
│   ├─ db-schema.md       데이터 구조   · api-spec.md  기능 명세
│   ├─ shared-types.ts    자료형 정의 (코드가 정본)
│   └─ design-guide.md    화면 디자인 규칙
└─ apps/web/            ← 실제 앱 코드

계약서(contracts/)는 건축의 설계도면과 같습니다 — 시공자(AI)가 마음대로 도면을 고치지 않고, 도면과 다르게 지어야 할 사정이 생기면 보고합니다.

1부 · 왜 바꿨나 — S2

필요하든 아니든, 매번 내는 비용이 있었다

예전 방식(레거시 파이프라인)은 AI 가 지금보다 서툴던 시절의 설계였습니다. 안전장치가 모든 도로의 과속방지턱처럼 모든 작업에 무조건 붙어 있었죠. 지금 필요한 것은 낭떠러지 커브에만 세우는 가드레일 — 위험한 지점에서만 작동하는 안전장치입니다.

① 컨텍스트 분절
일을 5개 역할 에이전트로 쪼개 markdown 문서로 전달 — 말 전달 게임처럼 전달마다 맥락이 샜다 (품질 손실 1순위)
② 모델 강등
작업 종류마다 더 저렴한(=약한) 모델을 배정하는 매트릭스 — 숙련공을 두고 견습생에게 맡긴 셈
③ Phase 부기
단계마다 관리 문서 5종 작성 의무 — 일하는 시간보다 기록하는 시간이 길었다
④ 상시 게이트
사소한 변경에도 외부 AI(codex) 검토 5~15분 대기 — 모든 서류가 결재줄에 선 격
⑤ 훅 택스
파일 하나 고칠 때마다 검사 프로세스(훅)가 돌았다 — 문 지날 때마다 보안검색대

다섯 개의 공통점: 그 작업에 필요한지 따지지 않고 매번 지불하는 비용이라는 것. hcg-core 는 이 다섯을 걷어내고, 위험한 지점(데이터 삭제·결제 같은 되돌리기 어려운 일)에만 안전장치를 남겼습니다.

2부 · hcg-core 사용법 — S4

넣은 것보다 뺀 것이 설계다

hcg-core 는 플러그인(Claude Code 에 끼우는 확장 기능) 하나로 설치됩니다. 안에 든 것과 일부러 뺀 것이 이렇습니다.

들어있는 것

  • 슬림 방법론 (Operating Rules §0~§5) — 작업 규칙 6개: §0 우선순위(충돌 시 정확성>안전>단순성>일관성) · §1 진행 vs 질문(되돌리기 쉬우면 진행, 비가역이면 질문) · §2 단순성(문제를 정확히 푸는 최소 코드) · §3 수술적 변경(요구된 것만 손댐) · §4 검증(→ S7) · §5 재앵커링(큰 행동 전 목표 재진술) — 그리고 "이 일은 이 길로" 라우팅 표(→ S5)
  • 풀스택 task-agent 1종 — DB·API·화면을 통째로 맡는 서브에이전트(일을 맡길 수 있는 보조 AI 작업자)
  • 컨벤션 스킬 — DB·백엔드·프론트엔드·검증·계약서 작성 규약
  • codex-review — 비가역·고위험 변경 때만 부르는 외부 AI 교차 검토 (온디맨드)
  • 워크플로 3종 — 대량 작업용 자동 편성(migrate·test-gen·converge)
  • SessionStart 훅 1종 — 세션이 열릴 때 프로젝트 상태 한 줄 안내

없는 것 (일부러 뺐다)

  • Phase 부기 파일 — 단계마다 쓰는 관리 문서
  • 상시 codex 게이트 — 모든 변경의 외부 검토 대기
  • 모델 배정 매트릭스 — 작업별 AI 강등 배정표
  • 역할 에이전트 5종 — 말 전달 게임의 주역들
  • 편집마다 도는 훅 — 파일 고칠 때마다 검사

오른쪽 목록이 낯익다면 맞습니다 — 전부 S2 의 다섯 가지 비용입니다. 빠진 게 아니라 뺀 것입니다.

2부 · hcg-core 사용법 — S5

어떤 작업이든 같은 길로 흐른다

내비게이션처럼 — 목적지가 어디든 안내 규칙은 하나입니다. 일을 시키면 AI 가 이 표를 보고 스스로 알맞은 길을 고릅니다. 외울 필요는 없고, "이런 길들이 있구나"만 알아두면 됩니다.

이런 일을 시키면이 길로 간다
보통의 기능 개발·수정·버그세션이 직접 하고, 끝나면 검증(§4)까지
서로 독립인 일 여러 개parallel-tasks — 작업자 여럿 동시 투입 (→ S6)
같은 수정을 파일 수십 개에migrate · test-gen 워크플로 (대량 자동 편성)
계약서와 실제 코드가 어긋났나 점검converge 워크플로 (읽기 전용 점검)
코드 리뷰/code-review — 내장 명령
되돌리기 어려운 변경·배포 직전codex-review — 외부 AI 교차 검토 (그때만)
  • 계약서(contracts/)가 단일 정답 — 코드가 계약과 다르면 코드를 고치거나 보고합니다. 계약 변경은 담당자와 합의한 뒤에만.
  • .claude/project.md 가 이 프로젝트의 값 — 기술 구성·경로·사용 규모가 여기 한 곳에 있고, AI 작업자는 일 시작 전에 반드시 읽습니다.
2부 · hcg-core 사용법 — S6 · 🆕 새 기능

기능 3개를 시키면 3배로 벌어진다

예전 방식은 작업자 1명이 순서대로 시공하는 현장이었습니다 — 일이 몇 개든 한 줄로 섰죠. 새 방식은 독립된 일이면 작업반을 여럿 동시에 투입합니다.

  • ① 먼저 서로 물리는 일인지 판정합니다 — 얽혀 있으면 순차로, 애매해도 순차로(안전 우선).
  • ② 독립이면 일 하나당 작업자(task-agent) 하나를 동시에 투입합니다. 같은 파일을 건드릴 것 같으면 작업 공간을 분리(worktree)해 충돌을 원천 차단.
  • ③ 작업자마다 DB·기능·화면을 통째로 만들고 스스로 검증까지 한 뒤 보고합니다.
  • ④ 마지막에 세션이 전체를 모아 통합 검증합니다.
2부 · hcg-core 사용법 — S7

검증을 "했다"가 아니라 "증명한다"

모든 작업은 끝나기 전에 검사를 통과해야 합니다. 검사는 강한 순서대로 사다리처럼 — 쓸 수 있는 가장 강한 단계를 씁니다.

  • 1단 · 자동화 테스트 — 고치기 전엔 실패하고, 고친 뒤엔 통과하는 테스트
  • 2단 · 타입·린트·빌드 — tsc/eslint/build 가 clean 하게 통과 (코드 조립·점검)
  • 3단 · 실행 스모크 — 실제로 켜서 코드 경로를 돌려보고 출력을 확인
  • 4단 · 명시 수용기준 + 사람 — 위가 다 불가능할 때, 기준을 명시하고 사람이 판정
모형 시험만 믿지 않는다 마네킹 충돌시험(모킹 — 실물 대신 모형으로 하는 테스트)만으로 출고하지 않습니다. 실제 사례: 모형 테스트 470건이 전부 통과했는데 실제 서버에선 100% 실패 — 그래서 DB·파일·문서 생성처럼 모형이 감추기 쉬운 곳은 한 번은 실물로 돌립니다.
개업 리허설엔 실제 손님 수만큼 개발 중엔 데이터가 몇십 건뿐이라 뭐든 빨라 보입니다. 그래서 프로젝트를 만들 때 "몇 명이 쓰나요?"를 묻고, 목록·집계·문서 생성은 그 규모의 데이터를 넣고 실측해 사람 말로 보고합니다. 보고 예시 — "✅ 목록 0.3초 · 지불증 만들기 1.2초 (3년치 18만 건 기준)" / "⚠ 10.7초 — 버튼 누르고 10초면 멈춘 줄 압니다. 원인: 압축된 글꼴을 만들 때마다 풀고 있어서."

검사를 통과한 작업 단위마다 커밋(게임 세이브처럼 작업 상태 저장)합니다 — 다음 세션이, 또는 사고로 끊긴 세션이 세이브 지점부터 이어서 합니다(→ S8).

2부 · hcg-core 사용법 — S8 · 🆕 새 기능

밤새 돌려도 끊기지 않는다

밤새 도는 공장처럼 — 사람이 없어도 일을 계속하고, 정전이 나도 멈춘 지점부터 이어서 합니다. 예전 방식에는 없던 기능입니다.

  • 한도로 끊겨도 자동 재개 — AI 사용량 한도에 걸리면 세션이 그 자리에서 죽습니다(안에서 "이어서 해"라고 말할 주체가 없음). 전용 러너(run-headless)가 밖에서 감시하다 폴백 모델(예비 AI)로 같은 세션을 이어서 돌립니다.
  • "조용한 미완주" 검출 — 끝났다고 종료했는데 실제론 일이 안 끝난 상태를 밖에서 잡아냅니다. (겉보기 정상 종료가 가장 위험합니다.)
  • 세이브 지점(커밋) 덕에 재개가 쌉니다 — 실측에서, 끊기기 전 저장해 둔 커밋 4개 덕분에 처음부터 다시 하지 않고 이어서 완주했습니다.
3부 · 실무 — S9

새 프로젝트는 명령 세 줄이면 선다

새 아파트 입주처럼 — 열쇠 받고(설치), 이사하고(init), 삽니다. 설치는 컴퓨터마다 한 번이면 됩니다.

# 머신당 1회 — 설치 claude plugin marketplace add Inpsyt/HCG_harness claude plugin install hcg-core@hcg-harness-marketplace # 프로젝트 폴더에서 새 세션을 열고 → /hcg-core:init

init 이 묻는 것은 세 가지뿐입니다:

  • ① 프로젝트 이름
  • ② 앱 골격을 만들지 — 빈 폴더면 "예", 이미 코드가 있는 프로젝트에 규칙만 얹으려면 "아니오"
  • ③ 사용 규모 — "이 프로그램을 몇 명이 쓰나요?" S7 실측의 기준이 됩니다. 몰라도 됩니다 — 500명 가정값으로 진행하고 나중에 바꾸면 됩니다.

끝나면 총 30파일이 생깁니다 — 하네스 레이어(.claude/ — 방법론·에이전트·스킬) + 계약서 4종(contracts/) + 앱 골격(Next.js+Prisma, 선택). 이후 통상 순서:

npm install # 의존성 설치 npx prisma generate # Prisma 클라이언트 생성 — 빼먹으면 빌드가 타입 오류로 깨집니다 npm run dev # 개발 서버 기동
3부 · 실무 — S10

이행은 프로젝트당 한 번, 짐은 버리지 않는다

이사와 같습니다 — 예전 방식으로 만든 프로젝트를 새 방식으로 옮기되, 짐(작업 이력·수정한 파일)은 버리지 않고 창고에 보관합니다.
