# Verification Ladder — Verify, Don't Assume

작업을 **검증 가능한 목표(checkable goal)**로 바꾼 뒤, 충족될 때까지 루프를 돈다. 작업이 허용하는 한 **가장 높은 rung**을 사용한다.

## 검증 사다리 (높은 rung 우선)

1. **자동화 테스트 (rung-1)** — 변경 전 실패하고 변경 후 통과하는 테스트.
   (최선 — 정의 가능한 I/O가 있는 모든 작업에 사용. 버그 수정: 실패하는 테스트로 먼저 재현한 뒤 고친다.)
2. **타입 체크 + lint + 컴파일/빌드 (rung-2)** — clean하게 통과.
3. **실행 가능한 스모크 체크 (rung-3)** — 실제로 코드 경로를 실행해 출력을 보여주거나, 정확한 수동 재현 절차를 제시한다.
4. **명시적 수용 기준(plain words) + diff (rung-4)** — 위 세 가지가 적용 불가할 때(UI·디자인·탐색적 작업·재현 어려운 동시성/환경 버그). 사람을 검증자로 만든다 — 명시적으로.

## 두 가지 가드

- **Anti-overfit:** 테스트는 *구현*이 아니라 *요구사항*을 포착해야 한다. 통과한 뒤 자문하라 — "코드가 여전히 틀렸는데도 이게 통과할 수 있는가?" 그렇다면 체크가 불충분한 것이다.
- **Weak criteria:** 성공이 정의되지 않았다면, 구체적 기준 2~3개를 사용자에게 제안하고 명시한 기본값으로 진행한다 — 숨은 타깃을 지어내지 말고, 완벽한 스펙을 기다리며 멈추지도 말 것.

## 적용 원칙

- 작업을 시작하기 전에 **목표 / 제약 / 검증 방법**을 한 줄로 재진술한다(긴 세션에서 규칙이 흐려질 때 재정렬용).
- 가능한 한 낮은 rung으로 내려가지 말고, 작업이 허용하는 가장 강한 rung을 택한다. rung-4(사람=검증자)는 다른 rung이 모두 불가할 때의 최후 수단이다.

## rung-1 이 무력한 두 경우 (실행 검증을 추가로)

아래 둘은 **rung-1 통과가 그 축에 대해 아무것도 증명하지 않는다.** rung-3 을 대체가 아니라
**추가로** 통과시킨다.

**(a) 모킹한 경계** — DB 트랜잭션 · 파일 IO · 바이너리/문서 생성 · 외부 어댑터 · 시간/랜덤.
모킹한 대상의 실제 동작에 대해 그 테스트는 아무 말도 하지 않는다. → **한 번은 실물로**
통과시킨다(실서버 1회 호출 · 실 DB 1건 · 실제 파일 생성).

> 실증: 단위 470건 green 인데 실서버 100% 실패한 사례 — `$transaction` 모킹이 "렌더 10초 vs
> 트랜잭션 기본 타임아웃 5초"를 가렸다. 실서버 스모크만 검출했다.

**(b) 데이터 규모·배포 형태에 민감한 경로** — 목록·검색·집계·리포트·문서 생성. 개발 시드(수십 건)
에서는 인덱스 유무·N+1·풀스캔이 전부 똑같이 빠르다(**신호 자체가 없다**). → `.claude/project.md`
「운영 규모」로 시드해 실측하고 아래 형식으로 보고한다. 배포 형태(런타임에 읽는 자산·외부 경로)는
**릴리스 직전 1회** 의존성 정리 상태에서 빌드·기동으로 확인한다(codex-review 트리거 ⑥과 동시점).

## 실측 결과 보고

**규율은 4개뿐이다.** 섹션 이름·이모지·톤은 예시이며 프로젝트가 바꿔도 된다.

1. 실측치를 **사람이 판단할 수 있게**(초 단위·체감 번역)  2. **판정을 숫자보다 먼저**
3. **근거 없는 추정 금지**(공수 "반나절"·개선 후 수치 "1초로")  4. **질문으로 끝내지 않기**
— 무인 실행이 멈춘다. "그대로 두고 진행했습니다"로 닫고 판단만 남긴다

**비례성**: 이 형식은 **여러 파일에 걸친 기능 단위** 작업의 것이다. 한 줄 수정·문구 변경에는
한두 문장이면 족하다. 해당 없는 항목은 통째로 생략한다.

체감(UX 통상): **~1초 쾌적 ✅ · 1~3초 괜찮음 ✅ · 3~10초 답답 ⚠️ · 10초~ 고장난 줄 안다 ⚠️**

정상이면 한 줄: `✅ 속도 — 목록 0.3초 · 지불증 만들기 1.2초 (3년치 18만 건 기준)`

목표를 넘겼으면 **체감 → 원인(사람 말) → 지금 상태** 순으로:

```
⚠️ 속도 — 지불증 만들기가 10.7초 걸립니다

   버튼을 누르고 10초를 기다려야 해서 "멈춘 것 같다"는 반응이 나올 수준입니다.
   원인: PDF 글꼴을 압축된 형태로 넣어둬서 만들 때마다 압축을 푸느라 시간이 걸립니다.
   그동안 데이터베이스를 붙잡고 있어서, 여러 명이 몰리면 다른 기능까지 느려집니다.
   개선 여지가 있습니다. 지금은 그대로 두고 진행했으니 고칠지 알려주세요.
```

**원인은 반드시 사람 말로** — "압축을 푸느라"는 비개발자도 이해하고 "압축 안 된 걸 쓰면
되잖아요"라고 되물을 수 있다.

**독자 구분**: 위는 **세션의 최종 사용자 보고** 형식이다. `task-agent` 완료 보고는 오케스트레이터가
읽으므로 **실측 수치만** 담으면 된다. 전체 구조(요약 앞·기술 상세 뒤)도 예시일 뿐이다.
