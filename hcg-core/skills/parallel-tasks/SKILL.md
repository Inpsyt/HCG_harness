# Parallel Tasks — Task 축 병렬 처리

병렬화의 단위는 역할(레이어)이 아니라 **Task** 다. 각 에이전트는 자기 Task 의 전 레이어
(db+api+ui)를 통째로 맡아 컨텍스트 분절(이음새 버그)을 만들지 않는다.

## 1. 결합도 판정 (dispatch 전 필수)

Task 쌍마다 3가지를 검사한다:

1. 같은 파일·모듈을 수정하나?
2. `contracts/` 등 공유 계약을 바꾸나?
3. 한 Task 의 설계 결정이 다른 Task 의 구현을 바꾸나?

하나라도 "예" → 그 Task 들은 **결합군**: 이 세션이 순차로 직접 수행한다. 전부 "아니오"인 것만
병렬 후보다. **애매하면 순차** — 오분류로 생기는 통합 버그가 병렬로 버는 시간보다 비싸다.

## 2. Dispatch

- 독립 Task 당 `task-agent` 1개를 **한 메시지에서 병렬** spawn 한다.
- 프롬프트 필수 요소: ① Task 정의 ② 수용 기준 ③ 관련 경로(`.claude/project.md` 기준)
  ④ 실행할 검증 명령.
- 파일 겹침 가능성이 조금이라도 있으면 `isolation: "worktree"` 를 건다.
- 동시 2~5개 권장. 그 이상이면 동질 작업인지 재검토 — 동질(같은 변환 × N 대상)이면
  `migrate`/`test-gen` 워크플로가 맞다.

## 3. 자체검증

각 task-agent 는 자기 Task 를 검증 사다리(verification-ladder)의 최강 rung 으로 검증하고,
변경 파일·검증 결과·"Noticed, not changed" 를 보고한다(task-agent 정의에 내장).

## 4. 통합

1. 전 에이전트 완료 후 결과를 수합한다 — 실패 에이전트는 보고에 명시하고 해당 Task 만 이 세션이
   순차 재수행한다.
2. worktree 사용 시: 각 브랜치의 변경을 병합하고 겹친 파일이 없는지 확인한다(겹침 발견 = 1단계
   판정 오류 — 해당 Task 를 순차로 재검토).
3. 병합된 트리에서 **전체 빌드/테스트를 1회** 실행한다 — 개별 검증이 전부 green 이어도 이 단계는
   생략하지 않는다.
4. 통합 보고: Task 별 결과 + 전체 게이트 결과.
